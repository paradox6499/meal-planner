# Telegram-бот с напоминаниями — архитектура

Ответ на вопрос "чем мы отличаемся от чата с ИИ": проактивность. Бот пишет
первым в нужный момент — чат этого сделать не может по своей природе (он
только отвечает). Это единственная часть продукта, которую нельзя
воспроизвести промптом, поэтому она заложена сюда отдельным документом
ещё до того, как заведён сам бот (см. блокер в конце файла).

## Ключевое отличие от текущей архитектуры

Сейчас **вся логика — на клиенте**: React-стейт живёт в браузере, исчезает
при закрытии вкладки, ничего не знает о времени суток. Напоминание должно
прийти пользователю, даже если он час назад закрыл приложение — то есть
план должен жить **на сервере**, а не только в `useState`. Это главное
структурное изменение, не косметика поверх текущего кода.

## Компоненты

```
┌─────────────────┐      initData (подпись HMAC)      ┌──────────────────┐
│  Mini App (React)│ ────────────────────────────────► │   Backend API     │
│  (текущий код,    │ ◄──────────────────────────────── │  (нужно написать) │
│   почти без правок)│      план / список покупок       │                    │
└─────────────────┘                                    └─────────┬────────┘
                                                                  │
                                                       читает/пишет│
                                                                  ▼
                                                         ┌──────────────────┐
                                                         │   База данных     │
                                                         │  (users, plans,    │
                                                         │   meal_slots)      │
                                                         └─────────┬────────┘
                                                                  │
                                                        каждые 5-15 мин
                                                                  ▼
                                                         ┌──────────────────┐
                                                         │  Scheduler/worker  │
                                                         │  (cron-процесс)     │
                                                         └─────────┬────────┘
                                                                  │ sendMessage
                                                                  ▼
                                                         ┌──────────────────┐
                                                         │   Telegram Bot API │
                                                         └─────────┬────────┘
                                                                  │
                                                                  ▼
                                                           Сообщение юзеру
```

### 1. Backend API (новый, сейчас не существует)

Минимум эндпоинтов:

- `POST /api/plan` — сохранить план недели (то, что сейчас живёт в
  `planState` в React). Тело — то же самое, что уже строит
  `buildInitialPlan()` в `App.jsx`, плюс `telegram_user_id` из `initData`.
- `GET /api/plan` — отдать текущий план (чтобы Mini App при повторном
  открытии не спрашивал всё заново).
- `PATCH /api/plan/meal` — swap блюда (то же, что сейчас `swapMeal()`
  делает локально) — переносим на сервер, чтобы бот в напоминании видел
  актуальное блюдо, а не то, что было при генерации плана.
- `POST /api/reminder-settings` — во сколько обычно ужинают/обедают
  (см. "Чего не хватает в данных" ниже).

Валидация личности — не логин/пароль, а проверка `initData`, которую
Telegram передаёт при открытии Mini App: HMAC-SHA256 подписанная строка,
проверяется секретом = хэшем токена бота. Официальная механика, не
самопальная — библиотеки типа `@telegram-apps/init-data-node` делают это
за вас.

### 2. База данных

```
users
  id (telegram_user_id, PK)
  first_name               -- приходит из initData, только для приветствия/отображения
  household_id            -- см. "семейный список" ниже
  timezone
  breakfast_time, lunch_time, dinner_time, snack_time   -- когда обычно ест
  reminder_lead_minutes    -- за сколько минут напомнить (по умолчанию 30-40)
  streak_weeks              -- см. "Аккаунт" в разделе 5, для достижений
  subscription_active_until  -- nullable, см. "Аккаунт" в разделе 5

plans
  id
  household_id
  week_start_date
  budget, family_size, diet, allergies, cuisines, devices   -- слепок выбора визарда

meal_slots
  id
  plan_id
  day_index (0-6)
  meal_type (breakfast/lunch/dinner/snack)
  recipe_id
  reminder_sent_at (nullable)   -- чтобы не напомнить дважды
```

`household_id`, а не привязка планов напрямую к `user_id` — сразу
закладываем то, что вы просили отдельно: общий список на семью с живой
синхронизацией. Несколько `telegram_user_id` в одной `household` видят
один и тот же `plan`.

### 3. Scheduler (новый процесс, не часть Mini App)

Простой cron/воркер, тикающий раз в 5-15 минут:

```
для каждого meal_slot, где:
  reminder_sent_at IS NULL
  AND сейчас >= (время приёма пищи пользователя - reminder_lead_minutes)
  AND сейчас < время приёма пищи (не слать напоминание постфактум)
→ отправить sendMessage через Bot API всем user_id из household_id
→ проставить reminder_sent_at
```

Текст сообщения — примерно:

> 🍝 Через 30 минут ужин: **Паста с томатным соусом**. Нужно 25 минут — самое
> время начинать. [Открыть рецепт]

Кнопка "Открыть рецепт" — deep link `t.me/<bot_username>/<app>?startapp=recipe_<id>`,
Mini App при старте читает `startapp`-параметр и сразу открывает нужную
модалку рецепта (это уже есть — `RecipeModal`, нужно только прокинуть
recipe id из параметра запуска вместо клика).

### 4. Фронтенд — что реально меняется в текущем `App.jsx`

Немного, при условии что backend есть:
- `handleFinish()` — после `buildInitialPlan()` дополнительно `POST /api/plan`.
- `swapMeal()` — дополнительно `PATCH /api/plan/meal`.
- При маунте — если у пользователя уже есть сохранённый план на сервере
  (открыл Mini App повторно в течение недели) — сразу показывать `ResultView`,
  а не гнать через визард заново.
- Новый маленький шаг в визарде (или просто разумные дефолты) — время
  приёмов пищи. Сейчас этого нет вообще, а без него не от чего отсчитывать
  "за 30 минут до".

### 5. Идентификация, приветствие, шеринг и вкладка «Аккаунт»

**Приветствие — уже сделано, бэкенд не нужен.** Telegram сам отдаёт имя
пользователя в `initDataUnsafe.user.first_name` при открытии Mini App —
никакого своего логина/регистрации заводить не нужно, это не пароль и не
секрет. `getTelegramFirstName()` в `App.jsx` читает его и показывает «Привет,
{имя} 👋» под названием приложения; вне Telegram (как в этом локальном
превью) просто ничего не показывает, а не подставляет заглушку.

**«Поделиться с семьёй» — тоже сделано, частично.** Кнопка на экране
результата собирает читаемый текст плана (дни, блюда, итоговая сумма) и
открывает `https://t.me/share/url?text=...` — штатный диалог Telegram
«переслать в чат», работает без бэкенда и без деплоя. Бот уже реальный —
**@s_edim_bot** («Съедим»), `BOT_SHARE_URL` в `App.jsx` теперь ведёт на
`https://t.me/s_edim_bot`, так что каждая пересылка плана уже сегодня несёт
кликабельную карточку с приглашением в бота (просто в сам бот, не в
конкретный план — см. ниже). У бота пока нет прикреплённого Mini App
(`getMe` вернул `has_main_web_app: false`) — это отдельный шаг через
@BotFather → Bot Settings → Menu Button/Mini App, и ему **нужен реальный
HTTPS-адрес**, то есть упирается в тот же блокер с хостингом. Чего пока нет
даже после этого: у сообщения нет кликабельной ссылки НАЗАД в конкретный
план — получатель попадёт в бота вообще, но не может тапнуть и открыть
именно тот план, которым с ним поделились. Это чинится
ссылкой вида `t.me/<bot>/<app>?startapp=plan_<id>` (`&url=` параметр в
`t.me/share/url`), а `plan_<id>` резолвится только если план сохранён на
сервере (см. таблицу `plans` выше) — то есть шеринг с реальной ссылкой это
не новая задача, а бонус к уже спроектированному backend'у из раздела 1-2.

**Вкладка «Аккаунт» — базовая версия уже сделана, без backend'а.**
Открывается по иконке-шестерёнке в шапке (`AccountView` в `App.jsx`,
профиль — `lib/profile.js`, localStorage). Что уже работает:

- Имя для приветствия (переопределяет имя из Telegram), переключатель темы
  Системная/Светлая/Тёмная (`data-theme` на `<html>`, поверх
  `prefers-color-scheme`).
- Профиль для плана — семья, приёмы пищи, рацион, аллергии, кухня, техника —
  сохраняется один раз, дальше визард при сборке плана спрашивает только
  магазин и бюджет (2 шага вместо 8). Это закрывает ту самую дыру в UX,
  которая упоминалась раньше («заново» стирало всё и гнало через 8 шагов).
- Карточка «Подписка» — пока честный placeholder («Free», список того, что
  откроет премиум), без реального списания — ни один провайдер не подключён.

Чего тут нет и не может быть без backend'а — то, что должно быть видно
**другим людям** или пережить смену устройства/очистку кеша:

- *Достижения/стрик* — например, «3 недели подряд уложились в бюджет».
  Технически — счётчик в `users` (`streak_weeks`), инкрементируется
  scheduler'ом раз в неделю, если план прошлой недели существовал и не был
  брошен на середине. Это не декор — прямое усиление поведенческого якоря
  (привычка), единственной настоящей защиты от копирования: чем длиннее
  стрик, тем больнее его бросить ради клона.
- *Синхронизация профиля между устройствами* — сейчас профиль живёт в
  localStorage конкретного браузера/WebView, на другом телефоне его не
  видно. Переезжает в `users` по `telegram_user_id`, когда появится backend.
- *Реальная подписка* — см. отдельный раздел ниже.

### Оплата — почему ЮKassa, а не (только) Stars

Официально Telegram Bot Payments требует Stars для **цифровых** товаров при
оплате через нативный `sendInvoice`. Но это правило касается конкретно
потока `sendInvoice`/`answerPreCheckoutQuery` — если оплата идёт **снаружи**
(открыли обычную хостед-страницу провайдера через `openLink`, а не
`sendInvoice`), формально это уже не «платёж через Telegram», и это ровно
то, как это делают другие мини-аппы с ЮKassa. Плюс для российской аудитории
это практичнее: чтобы купить Stars, обычно нужен Apple/Google In-App
Purchase, а с российскими картами это часто не работает.

Поток:

```
Аккаунт → «Оформить подписку»
  → openLink на хостед-страницу оплаты ЮKassa (сумма + telegram_user_id в metadata)
  → пользователь платит картой/СБП на стороне ЮKassa
  → ЮKassa шлёт webhook POST /api/payments/webhook на backend
  → backend проверяет подпись уведомления, находит user по metadata,
    ставит users.subscription_active_until = now() + 30 дней
  → Mini App при следующем открытии видит активную подписку (обычный GET /api/plan
    или отдельный GET /api/account, см. раздел 1)
```

Нужно от вас, когда будете готовы: аккаунт ЮKassa (самозанятый/ИП/ООО —
без регистрации как продавец принимать платежи нельзя), `shop_id` и
`secret_key` оттуда. Дальше — один эндпоинт-вебхук на backend (несколько
часов работы) и колонка `subscription_active_until`, которая уже заложена
в схему `users` выше.

## Чего не хватает в данных прямо сейчас

Визард спрашивает **какие** приёмы пищи (завтрак/обед/ужин/перекус), но не
**когда**. Для напоминаний это обязательно нужно. Самый дешёвый вариант —
не отдельный шаг, а один слайдер/пара инпутов на шаге "Приёмы пищи":
"обычно ужинаете в ___" с разумным дефолтом (13:00 / 19:00), не блокирующий
для тех, кто торопится пройти визард.

## Что нужно, чтобы начать (блокер, о котором говорили раньше)

1. Бот через @BotFather — токен и username.
2. Хостинг под backend + scheduler (не Mini App — тот статикой можно и на
   Vercel/GitHub Pages, но `sendMessage` должен вызываться откуда-то с
   постоянно работающим процессом, значит нужен настоящий сервер/serverless
   с cron, не просто статический хостинг).
3. БД — на старте хватит SQLite (как в grocery-budget), при росте — Postgres.

## Порядок работ (грубая прикидка, без бота ничего не потестировать вживую)

1. Backend API + БД (эндпоинты выше) — **1-2 дня**, чистый код без внешних
   зависимостей от Telegram, тестируется как обычный HTTP API.
2. Проверка `initData` — **несколько часов**, есть готовые библиотеки.
3. Scheduler + интеграция с Bot API `sendMessage` — **1 день**, но
   тестируется только на реальном боте (см. блокер).
4. Правки в `App.jsx` под серверный план вместо чисто локального стейта —
   **1 день**.
5. Deep link на конкретный рецепт по `startapp` — **несколько часов**.

Итого **~4-5 дней** после того, как появится бот и хостинг — заметно
меньше, чем починка скрейперов, и не требует живых цен вообще: можно
собрать и обкатать полностью на оценочных ценах.
