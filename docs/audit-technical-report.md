## 1. Коротко

Серверная часть написана аккуратно, по безопасности заметно выше среднего для проекта такой стадии. Идентичность пользователя везде берётся из подписанного initData. Вебхуку ЮKassa сервер не верит: статус перепроверяется запросом к самой ЮKassa. Гонки на одном инстансе исключены самой структурой кода.

Но в самом свежем изменении («серверная проверка бесплатного лимита», коммит 7dd1dfc) есть баг, который **ломает главный цикл удержания и сжигает оплаченные покупки**: лимит списывается при каждом открытии приложения с сохранённым планом и при каждой замене блюда. Второе: дайджест, `/report` и пересылка обращений в поддержку почти наверняка молча не доходят из-за Markdown. Третье: по 152-ФЗ политика конфиденциальности расходится с кодом, удаление данных технически не реализовано.

**Показывать инвестору как демо можно. Брать деньги с реальных пользователей до исправления пунктов 1–4 из раздела 5 нельзя.**

## 2. Сильные стороны

1. **Граница доверия проведена правильно.** `telegramUserId` всегда берётся из initData, а не из тела запроса (`server/src/app.js:285-294`, family, referral). HMAC сравнивается через `timingSafeEqual`, `auth_date` ограничен 24 часами (`server/src/initData.js:44-52`). Статус платежа берётся только из `fetchPaymentStatus` (`server/src/app.js:842`). Секрет Telegram-вебхука проверяется, админские команды ограничены по chat_id.
2. **Гонок нет по построению.** `DatabaseSync` + один процесс + ни одного `await` между проверкой и записью: лимит в `app.js:372-388`, идемпотентность вебхука в `app.js:843-866`, реферал помечается до `await` в `referrals.js:62`. **Этот инвариант нигде не записан**: один добавленный `await` вернёт гонки.
3. **Ноль runtime-зависимостей и чистые функции** (`reminderTiming`, `planReplyForUpdate`, `parse*`, `computePlanStatus`): переезд на другой хостинг за час, 293 теста за 4 секунды.
4. **Сбои ВкусВилл обработаны и протестированы.** Ретраи на 429/5xx/таймаут, отдача устаревшей цены вместо «нет цены» (`server/src/vkusvillPrices.js:185-197`), откат на статические рецепты (`src/App.jsx:536-539`).
5. **Email для чека на сервере не хранится**: только localStorage и транзитом в ЮKassa.

## 3. Слабые места (по вероятности × ущербу)

### #1. Лимит расходуется при открытии приложения и заменах блюд [ПОДТВЕРЖДЕНО] — КРИТИЧНО

`src/App.jsx:464-466`:
```js
useEffect(() => {
  if (done && planView) submitPlanToBackend(planView, mealTimes);
}, [done, planView, mealTimes]);
```
Эффект вызывает `POST /api/plan` при монтировании с сохранённым в localStorage планом (`done = !!initialActiveSlot`, `App.jsx:175`), на каждый `swapMeal`, повтор цен, переключение и удаление слота, правку времени приёмов пищи. Сервер на **каждый** успешный `/api/plan` пишет `plan_generated` и при исчерпанном базовом лимите списывает кредит (`server/src/app.js:387-388`).

Как это ломается:
- **Бесплатный пользователь возвращается через 7+ дней**, в том числе по «напоминанию вернуться» (`server/src/scheduler.js: runFreeNudgeTick`). Открытие со старым планом отправляет `/api/plan` → лимит потрачен. «Заново» → визард → `handleFinish` → «лимит исчерпан».
- **Купил «ещё один план» за 59 ₽**, потом открыл приложение или заменил блюдо: кредит сгорает до сборки нового плана. Воспроизведено: `credits 1 → 0`, `usedThisWeek 2`, `canGenerate: false`.
- У Pro-пользователей каждое открытие и замена раздувают `usedThisWeek`, это ведёт к #2. Метрика «планов собрано» в дайджесте бессмысленна.

Исправление: полдня. Если не исправить: бесплатная воронка не работает, продукт за 59 ₽ фактически не выдаётся, будут возвраты и претензии.

### #2. Формула кредитов неверна даже без #1 [ПОДТВЕРЖДЕНО] — КРИТИЧНО

`server/src/app.js:376` и `server/src/app.js:210`: условие `usedThisWeek >= FREE_PLANS_PER_WEEK + extraPlanCredits`. `usedThisWeek` (`server/src/db.js:746`) считает все `plan_generated` за 7 дней, включая сборки, уже оплаченные кредитами, и сборки времён Pro.
- **Вторая покупка в том же 7-дневном окне:** бесплатный план → купил кредит → собрал → купил второй кредит → `used=2, credits=1 → canGenerate:false`. Заплатил, ничего не получил.
- **Pro истёк** после 4 сборок за неделю → купил кредит → `used=4, credits=1 → canGenerate:false`.

Исправление: 2–3 часа (см. раздел 5, п. 2).

### #3. Дайджест, `/report` и обращения в поддержку не доставляются [ПО КОДУ] — ВЫСОКИЙ

`server/src/telegram.js:19`: `parse_mode: opts.parseMode ?? "Markdown"`. В `server/src/digest.js:108` передаётся `{ parseMode: undefined }`, и `undefined ?? "Markdown"` всё равно даёт Markdown. В legacy Markdown у Telegram непарный `_` или `*` вызывает 400 «can't parse entities».
- В дайджест попадают сырые имена событий без подписи в `EVENT_LABELS` (`digest.js:339-353` против реальных событий в App.jsx): `family_created`, `family_left` (одно `_`), `extra_plan_modal_opened`, `extra_plan_buy_clicked`, `plan_slot_add_started`, `recipe_video_search_clicked` (три `_`). При ошибке watermark не сдвигается (`digest.js:109`), окно только растёт, поэтому **дайджест и `/report` ломаются навсегда после первого такого события**. Ошибка видна только в логах Render.
- Обращения в поддержку тоже пересылаются админу в Markdown (`app.js:917`, текст из `webhook.js:35`). «Не работает s_edim_bot» или «*кнопка» не дойдёт. `/feedback` (`app.js:908`) ломается, пока такое обращение входит в последние 10.
- Напоминание (`telegram.js: buildReminderText`) вставляет `recipeName` в `*...*` без экранирования.

Как проверить: поискать `can't parse entities` в логах Render. Исправление: 30 минут.

### #4. Оплата подтверждается только вебхуком, страховки нет [ПО КОДУ] — ВЫСОКИЙ
- Если вебхук не дошёл (неверный URL — этот риск назван в `docs/launch-checklist.md`; или сервер лежал дольше окна ретраев ЮKassa), платёж навсегда остаётся `pending`. Повторной проверки нет, алерта нет.
- Ветка «платёж не наш» (`server/src/app.js:847-850`) молча отвечает 200, хотя в `metadata.telegram_user_id` есть получатель.
- После оплаты бот не присылает подтверждения. `return_url` ведёт в пустой чат бота (`app.js:782`), экран лимита в Mini App остаётся со старым состоянием.
- `idempotenceKey = randomUUID()` на каждый HTTP-запрос (`app.js:778`), поэтому комментарий в `yookassa.js` про защиту ретрая от дубля не соответствует действительности.
- Если ЮKassa подписана на `refund.*`, `object.id` будет id возврата → `fetchPaymentStatus` 404 → 500 → бесконечные ретраи. При возврате Pro не отзывается.

Исправление: 3–4 часа.

### #5. Один пользователь может заполнить диск и подвесить ВкусВилл для всех [ПО КОДУ] — СРЕДНИЙ/ВЫСОКИЙ
- `/events`: 60 запросов в минуту (`app.js:62`) по 4000 байт `props` (`app.js:40`), срока хранения у `events` нет. Это около 350 МБ в сутки с одного аккаунта при диске в 1 ГБ.
- `/api/prices`: 6 запросов × 300 выдуманных названий в минуту (`app.js:34`, `app.js:69`). Каждое название навсегда пишется в `ingredient_prices`, и по каждому уходит живой запрос к ВкусВилл, у которого один rate-limit на всех.
- Когда диск кончится, SQLite перестанет писать и ляжет всё, включая обработку платежей. Бэкап через `sendDocument` перестанет проходить после 50 МБ и сломается тихо (`backup.js:346-348`).

Исправление: 2–3 часа.

### #6. 152-ФЗ: `public/privacy.html` не совпадает с кодом [ПО КОДУ] — СРЕДНИЙ (растёт с продажами)
- **Хранится, но не заявлено:** тексты обращений (`feedback`, бессрочно), история планов (`plan_history`, 12 последних), связи рефералов (`referrals`).
- **Заявлено, но неверно:** аллергии и диета на сервер не уходят (только localStorage). Фраза «ЮKassa… минуя сервера Оператора» неверна: email проходит через `app.js:762`.
- **Трансграничная передача и локализация:** основная БД на Render (не в РФ), полный дамп ежедневно уходит в Telegram-чат админа (`server/src/backup.js:335-345`). Ни хостинг, ни бэкапы в политике не упомянуты. Требование ч. 5 ст. 18 152-ФЗ (первичная запись в БД в РФ) не выполняется.
- **Удаление обещано (п. 6 политики), но не реализовано:** ни скрипта, ни эндпоинта. Данные пользователя лежат в 10 таблицах (`users`, `meal_slots`, `events`, `plan_history`, `feedback`, `payments`, `referrals` в обеих ролях, `family_members`, `families`/`family_pantry` у владельца). Копии в бэкапах в Telegram не удалить. Очистка неактивных пользователей (п. 5) тоже не реализована.
- Внутри Mini App нет ссылок на политику и оферту: они только на лендинге в `index.html:135-136`. Перед оплатой согласие с офертой не запрашивается.

### #7. Миграции без версий, апгрейд старой схемы не тестируется [ПО КОДУ] — СРЕДНИЙ
`ensureColumn` (`server/src/db.js:23-27`) умеет только добавлять колонку. Нет `PRAGMA user_version`, нет упорядоченного списка миграций, нельзя переименовать колонку, сменить ограничение или перенести данные. Все тесты работают на `:memory:`, из-за этого уже был инцидент на проде с `is_pro` (`db.js:203-218`). Стратегический п. 1 на этой схеме будет болезненным.

### #8. Слабая связь: визард зависает без отклика [ПО КОДУ] — СРЕДНИЙ
`src/App.jsx:494`: `await checkPlanStatus()` без таймаута (`src/lib/backend.js:90`), `setAssembling(true)` только после ответа. Кнопка «Собрать список» (`App.jsx:1142-1152`) не блокируется на время ожидания: на медленной сети ничего не происходит, повторный тап снова запускает `handleFinish`. Ни у одного вызова в `backend.js`, кроме `sendSupportPrompt`, нет таймаута.

### #9. Мелкие проблемы
- **Порча UTF-8 в теле запроса [ПОДТВЕРЖДЕНО].** `server/src/app.js:96`: `raw += chunk` разрезает кириллический символ на границе чанка. Тело ~100 КБ даёт 4 символа `�` в сохранённой истории плана. Кроме того, после `req.destroy()` на 1 МБ промис никогда не завершается.
- **Реферер не проверяется** (`server/src/referrals.js:34-50`): `?startapp=ref_1` (любое число) даёт любому новому пользователю 7 дней Pro и создаёт мусорную строку `users` для несуществующего id.
- **Тики планировщика могут накладываться** (`server/src/index.js:77`): `setInterval` с async-тиком, у `sendTelegramMessage` нет таймаута, `markReminderSent` вызывается после `await` (`scheduler.js:30-31`). Тик длиннее 5 минут → повторные напоминания.
- **Семья работает после окончания Pro у владельца:** `join` и `pantry` тариф не проверяют (`app.js:626-691`). Владелец не может исключить участника, код приглашения не меняется.
- **Зачёркнутая цена «399 ₽»** (`src/App.jsx:2177`): если по ней никогда не продавали, это риск по закону о рекламе и ЗоЗПП.
- **Цены и лимиты продублированы на клиенте:** `EXTRA_PLAN_PRICE_RUB` (`App.jsx:1736` и `app.js:89`), `REFERRAL_REWARD_DAYS_LABEL` (`App.jsx:1828`), `MAX_FAMILY_MEMBERS_LABEL` (`App.jsx:1838`), 299 ₽ захардкожено в `App.jsx:2178`.
- **Логика ВкусВилл вручную продублирована** между `server/src/vkusvillPrices.js` и `src/lib/vkusvillMcp.js` (признано в шапке файла).
- **IP для лимита вебхука ЮKassa** берётся из подделываемого `x-forwarded-for` (`app.js:836`). Мелочь.

## 5. Топ-5 на эту неделю

1. **Разделить `/api/plan`.**
   - `POST /api/plan/generate` проверяет лимит, пишет `plan_generated`, списывает кредит. Вызывается один раз из `handleFinish`.
   - `POST /api/plan` (или `/api/plan/sync`) только заменяет `meal_slots` для напоминаний, без учёта и без 403. Его вызывает эффект `App.jsx:464`.
   - Тест: повторный sync с тем же планом не меняет `usedThisWeek` и `extra_plan_credits`.
2. **Исправить формулу кредитов.**
   - Писать `plan_generated` с `props.source: "free" | "credit" | "pro"`.
   - Лимит считать только по `source = "free"`: `canGenerate = isPro || freeUsed < FREE_PLANS_PER_WEEK || credits > 0`.
   - Кредит списывать, только если бесплатный лимит исчерпан и пользователь не Pro.
   - Три сценария из приложения A превратить в тесты.
3. **Отключить Markdown по умолчанию.**
   - В `telegram.js` без явного `parseMode` не отправлять `parse_mode`.
   - Напоминание: либо без разметки, либо HTML с экранированием `recipeName`.
   - Тесты: дайджест с событием `family_created`, обращение с текстом `s_edim_bot`.
   - Заодно добавить недостающие подписи в `EVENT_LABELS`.
4. **Сверка платежей.**
   - Вынести из вебхука `applyPaymentStatus(db, status)`.
   - Вызывать её ещё и из `/api/plan-status` для `pending`-платежей этого пользователя младше 48 часов (через `fetchPaymentStatus`).
   - На переходе в `succeeded` отправлять сообщение «Оплата прошла, Pro до …» или «План доступен».
   - В дайджест добавить строку «pending старше 1 ч: N».
5. **Ограничить рост БД.**
   - `MAX_PROPS_JSON_LENGTH` поставить 500, добавить суточный лимит событий на пользователя.
   - В `/api/prices` ходить живьём не более чем за ~60 промахами кэша на запрос.
   - В дайджест добавить размер БД (`page_count * page_size`) и время последнего успешного бэкапа.
   - Попутно за 15 минут: `readJsonBody` на `Buffer.concat(chunks).toString("utf8")` и `reject` при превышении размера.

Бонус на 15 минут: в `claimReferral` требовать `userExists(db, referrerTelegramId)`.

## 6. Топ-3 стратегических

1. **Вынести права доступа из аналитики.** `events` сейчас одновременно аналитика и источник правды для денег. Нужны отдельные таблицы: `plan_generations(telegram_user_id, created_at, source)` и учёт кредитов со ссылкой на `payment_id`. Плюс версионированные миграции через `PRAGMA user_version` и тест, который поднимает снимок старой схемы и прогоняет `openDb`. 3–5 дней.
2. **Трек соответствия 152-ФЗ.**
   - Хостинг в РФ (Yandex Cloud, Selectel или Timeweb Cloud; при нуле зависимостей переезд тривиален).
   - Бэкапы в российское объектное хранилище вместо Telegram.
   - Уведомление в Роскомнадзор (обработка и трансграничная передача).
   - `server/scripts/delete-user.js` и задача очистки неактивных.
   - Новый текст `privacy.html` по фактическим таблицам.
   - Ссылки на оферту и политику и согласие в `ProModal` и `ExtraPlanModal`.
   - 1–2 недели, включая юриста.
3. **Резать `App.jsx` по побочным эффектам, а не по количеству строк.**
   - Хуки `useEntitlements` (статус, лимит, оплата), `usePlanSlots`, `useFamily`.

## Приложение A. Скрипт воспроизведения #1 и #2

Запуск из корня репозитория: `node repro.mjs` (Node ≥ 22.5). Внешних зависимостей нет, используется настоящий `createApp` с in-memory БД.

```js
import { createHmac } from "node:crypto";
const S = new URL("./server/src/", import.meta.url).href;
const { openDb, addExtraPlanCredit, getExtraPlanCredits, setUserPro } = await import(S + "db.js");
const { createApp } = await import(S + "app.js");
const TOKEN = "1:T";
function initData(id) {
  const f = { user: JSON.stringify({ id, first_name: "T" }), auth_date: String(Math.floor(Date.now() / 1000)) };
  const dcs = Object.entries(f).sort(([a], [b]) => (a < b ? -1 : 1)).map(([k, v]) => `${k}=${v}`).join("\n");
  const sk = createHmac("sha256", "WebAppData").update(TOKEN).digest();
  return new URLSearchParams({ ...f, hash: createHmac("sha256", sk).update(dcs).digest("hex") }).toString();
}
const db = openDb(":memory:");
const srv = createApp(db, { botToken: TOKEN });
await new Promise((r) => srv.listen(0, r));
const base = `http://127.0.0.1:${srv.address().port}`;
const slot = { scheduledDate: "2026-09-28", mealType: "dinner", mealLabel: "Ужин", mealTime: "19:00", recipeName: "Паста" };
const post = (p, id, b = {}) => fetch(base + p, { method: "POST", body: JSON.stringify({ initData: initData(id), ...b }) }).then(async (r) => [r.status, await r.json()]);
const plan = (id) => post("/api/plan", id, { timezoneOffsetMinutes: 180, mealSlots: [slot] });
const status = async (id) => (await post("/api/plan-status", id))[1];

// A: купил extra-plan, затем открыл приложение / заменил блюдо (эффект App.jsx:464 шлёт /api/plan)
await plan(1); addExtraPlanCredit(db, 1);
await plan(1); console.log("A credits:", getExtraPlanCredits(db, 1), await status(1)); // credits 0, canGenerate false

// B: вторая покупка в том же 7-дневном окне
await plan(2); addExtraPlanCredit(db, 2); await plan(2); addExtraPlanCredit(db, 2);
console.log("B", await status(2)); // used 2, credits 1, canGenerate false

// C: Pro истёк, покупает extra-plan
setUserPro(db, 3, true); for (let i = 0; i < 4; i++) await plan(3); setUserPro(db, 3, false); addExtraPlanCredit(db, 3);
console.log("C", await status(3)); // used 4, credits 1, canGenerate false
srv.close();
```

Фактический вывод на `70aae84`: A — `credits: 0, usedThisWeek: 2, canGenerate: false`; B — `usedThisWeek: 2, extraPlanCredits: 1, canGenerate: false`; C — `usedThisWeek: 4, extraPlanCredits: 1, canGenerate: false`.
