## 2. Принципы

1. **Ноль изменений поведения.** Каждый этап — только перенос; никаких «заодно поправлю».
2. **Один этап — один коммит**, после каждого — полная проверка (раздел 5). Откат — `git revert` одного коммита.
3. **Зависимости идут в одну сторону:** `styles.js`/`constants.js` → компоненты → `App.jsx`. Циклических импортов нет.
4. Публичный экспорт `buildShareUrl` из `App.jsx` сохраняется (его импортирует `src/App.share.test.js`).

## 4. Этапы

**Этап 1 — перенос листовых компонентов и стилей (без изменения логики).**
Порядок (от того, от чего зависят остальные): `styles.js` → `constants.js` → `components/common.jsx` →
`RecipeModal.jsx` → `ProModals.jsx` → `components/account/*` → `ResultView.jsx` → `LastPlanGateView.jsx`.
Для каждого файла: вырезать код как есть, добавить `import`/`export`, импортировать обратно в `App.jsx`.
Общие вспомогательные функции, которыми пользуются и `MealPlanner`, и вынесенные компоненты
(`pluralPeople`, `formatResetDate`, `pluralDaysRu`, …), — в `src/lib/format.js`.

**Этап 2 — хуки вокруг `MealPlanner`.** Вынести группы состояния и эффектов, которые не пересекаются:
`usePlanStatus` (тариф, лимит), `useFamily`, `usePlanSlots`, `useReferral`, `usePriceRetry`
(автоповтор цен), `useWizardProfile`. `MealPlanner` остаётся склейкой. Это самый рискованный этап
(порядок эффектов, замыкания), делать после этапа 1 и по одному хуку за коммит.

**Этап 3 (опционально).** Тесты на компоненты (jsdom + Testing Library) для самых хрупких мест:
окно рецепта (портал), баннер деградации, история планов, пауза семьи.

## 5. Проверка после каждого этапа

1. `npm test` (фронтенд, сейчас 289), `npm run build`.
2. **Статическая проверка неопределённых имён** — самая частая ошибка при переносе (сборка её не ловит, это
   ошибка времени выполнения): ESLint с `no-undef` и `react/jsx-no-undef`, `react/jsx-uses-vars`
   (одноразовым запуском, без добавления в проект).
3. **Проход по экранам в браузере** (ширина 375 px, настоящий локальный бэкенд, `#tgWebAppData=…`, как в
   `docs`/памяти проекта): новичок — все шаги визарда; готовый план; рецепт; замена блюда; Аккаунт с историей, семьёй,
   рефералами; окна Pro и «ещё один план»; экран лимита; деградированный план (имитация отказа каталога); консоль без ошибок.
4. Сравнение размера сборки до/после (сильное расхождение — повод посмотреть).

**Ответы на вопросы раздела 7**

1. *Хватает ли проверки для этапа 1?* Да: перенос механический, сверка строк + ESLint закрывают
   главный риск (неопределённые имена). **Для этапа 2 — нет.** До него нужны 3–4 теста на `MealPlanner`
   в jsdom (Testing Library, бэкенд замокан) на денежные инварианты: открытие с сохранённым планом →
   ни одного `/api/plan/generate`; сборка → ровно один; деградированная сборка → ноль, после удачного
   повтора цен → один; экран лимита при `canGenerate:false`. Именно их сломает потеря замыкания.
2. *Порядок этапа 2.* Начинать с независимого и простого: `useTheme`/`useHomeScreen` → `useFamily` →
   `useReferral` → `usePlanStatus`. **`usePriceRetry` отдельно не выносить**: автоповтор цен,
   `handleRetryPrices`, `runFinish`, `pools`/`priceByName`/`planState`/`generationPending` делят одно
   состояние — это один хук `usePlanBuilder`. Подводные камни: (а) эффекты запуска отправляют запросы
   (`plan-status` ×3–4, семья, заявка реферала, синхронизация плана) — вызывать хуки в том же порядке,
   в каком сейчас объявлены эффекты, иначе меняется порядок запросов на сервер (заявка реферала до
   синхронизации плана важна: синхронизация создаёт строку `users`); (б) автоповтор цен держится на
   свежем замыкании `handleRetryPrices` при отключённом `exhaustive-deps` (`App.jsx:509`) — при переносе
   легко получить устаревшие `pools`.
3. *Переписать ли `runFinish` до разреза?* Да, частично и отдельным коммитом. Решение «сборка
   вырожденная или нет» и «засчитать сборку + положить в историю» сейчас продублировано в `runFinish` и
   `handleRetryPrices` (проверка «рецепты из каталога» трижды: `App.jsx:463`, `:497`, косвенно `:632`).
   Вынести чистую `assessPlanBuild({ store, catalogError, view, pools }) → { degraded, reason }` в
   `src/lib/` с тестами и один путь `completeGeneration(view)` с защитой «ровно один раз» через `useRef`
   по id слота, а не через `generationPending` из замыкания (после `await` замыкание может быть
   устаревшим, и двойной `reportPlanGenerated` спишет лишний кредит).
4. *TypeScript/JSDoc?* TypeScript — отдельная задача, не смешивать с разрезом. JSDoc на возвращаемые
   значения новых хуков — да, дёшево и помогает ревью этапа 2.
5. *Что ещё из стратегического п. 3.* (а) Цены и лимиты с сервера: после этапа 1 клиентские копии
   `PRO_PRICE_RUB`/`EXTRA_PLAN_PRICE_RUB` живут в одном месте (`components/ProModals.jsx`) — следующий
   маленький шаг отдавать их в `/api/plan-status`; (б) убрать лишние параллельные `checkPlanStatus` при
   запуске — естественно внутри `usePlanStatus`, но это изменение поведения, отдельным коммитом после
   разреза; (в) интеграционные тесты из п. 1 — они и есть «защитная сетка» стратегического пункта.
