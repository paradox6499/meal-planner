# meal-planner-server

Бэкенд бота **@s_edim_bot**: напоминания о еде, событийная аналитика,
бесплатный лимит / Pro / разовая покупка «ещё один план», оплата через
ЮKassa (с автоматической сверкой и возвратами), история планов, общий список
на семью, рефералы, приём обращений в поддержку в чате с ботом, удаление
данных пользователя. Ноль runtime-зависимостей (`node:sqlite`, `node:http`),
один процесс, один диск.

Как это работает: фронтенд после каждого изменения плана шлёт сюда
`POST /api/plan` (название рецепта на каждый день + во сколько обычно этот
приём пищи) — это только синхронизация для напоминаний, без учёта лимита;
реальную сборку плана фронтенд отдельно сообщает в `POST /api/plan/generate`
(один раз на сборку — там живёт бесплатный лимит и списание кредитов).
Сервер раз в 5 минут проверяет, не наступило ли время какого-то приёма пищи
в ближайшие `reminder_lead_minutes`, и если да — шлёт сообщение через
Telegram Bot API.

## Локальный запуск (проверить, что всё работает, до деплоя)

```bash
cd server
npm install
npm test                      # тесты, ничего внешнего не требуют
TELEGRAM_BOT_TOKEN=<токен бота от @BotFather> npm start
```

Без `TELEGRAM_BOT_TOKEN` сервер откажется стартовать — специально, чтобы не
запустить его "наполовину" в проде.

## Деплой — что нужно сделать вам (я не могу заводить аккаунты за вас)

Рекомендую **Render** — из трёх вариантов, что обсуждали (Render/Railway/
Fly.io), у него самый простой UI без командной строки, что важно, раз вы не
программист. Занимает минут 10-15.

1. **Зарегистрируйтесь на [render.com](https://render.com)** — можно через
   GitHub-аккаунт, это упростит следующий шаг.

2. **New → Web Service** → выберите репозиторий `paradox6499/meal-planner`.

3. В настройках сервиса укажите:
   - **Root Directory**: `server` (важно! иначе Render попытается собрать
     фронтенд, а не сервер)
   - **Runtime**: Node
   - **Build Command**: `npm install`
   - **Start Command**: `npm start`
   - **Instance Type**: **Starter** (~$7/мес), НЕ Free — на бесплатном
     тарифе Render "усыпляет" сервис после 15 минут простоя, а нам нужно,
     чтобы он проверял время каждые 5 минут без остановки. Это тот самый
     небольшой постоянный расход, который вы уже одобрили.

4. **Добавьте диск** (Render → ваш сервис → Disks → Add Disk) — без этого
   база данных (сохранённые планы) будет стираться при каждом обновлении
   кода:
   - **Mount Path**: `/data`
   - **Size**: 1 GB (с большим запасом)

5. **Переменные окружения** (Environment → Add Environment Variable):
   - `TELEGRAM_BOT_TOKEN` — токен бота от @BotFather (тот же, что уже
     использовался при настройке @s_edim_bot)
   - `DB_PATH` — `/data/data.db` (путь на диск, который добавили в шаге 4)
   - `ADMIN_TELEGRAM_ID` *(необязательно, но настоятельно рекомендуется)* —
     ваш личный telegram_user_id (узнать у @userinfobot). Включает сразу две
     вещи на этот же id: ежедневный отчёт по событиям/ошибкам (`src/digest.js`)
     и периодический бэкап БД файлом прямо в личку (`src/backup.js`). Не
     задана — обе отключены, ничего не ломается. Важно: Telegram не даёт боту
     писать первым — прежде чем это заработает, один раз напишите что угодно
     боту @s_edim_bot сами.
   - `DIGEST_HOUR` *(необязательно, по умолчанию 9)* — час по UTC, после
     которого раз в сутки уходит отчёт.
   - `BACKUP_INTERVAL_HOURS` *(необязательно, по умолчанию 24)* — как часто
     слать файл БД (`VACUUM INTO` — консистентный снимок, не сырая копия
     файла на лету). На небольшом масштабе файл весит копейки, раз в сутки
     с запасом.
   - `TELEGRAM_WEBHOOK_SECRET` *(необязательно, но нужен для приветствия
     новым пользователям и команды `/report`, см. ниже)* — придумайте любую
     длинную случайную строку (например, `openssl rand -hex 24` в терминале
     Mac, или просто набор случайных символов) и впишите её сюда же и в
     команду `setWebhook` в шаге 9.
   - `HASH_SECRET` *(рекомендуется)* — любая длинная случайная строка: ключ для
     необратимых хэшей "надгробий" удалённых аккаунтов (защита от обнуления
     лимита и повторной реферальной награды через «Удалить мои данные»). Не
     задан — используется токен бота, но тогда при его смене старые надгробия
     перестанут совпадать. Меняйте только если готовы потерять эту защиту.
   - `WEBAPP_URL` *(необязательно)* — адрес Mini App для кнопки «Открыть
     «Съедим»» в сообщении об оплате; по умолчанию GitHub Pages. Нужен при
     переезде фронтенда на другой хостинг/домен.
   - `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY` *(необязательно — без них
     оплата Pro просто отключена, `POST /api/pay/create` вернёт 503, всё
     остальное работает как раньше)* — оба значения из личного кабинета
     ЮKassa (Настройки → API). `YOOKASSA_SECRET_KEY` — секрет, никогда не
     вставляйте его в чат/код/коммит, только сюда, в переменные окружения
     Render. После деплоя добавьте URL вебхука в личном кабинете ЮKassa
     (Настройки → HTTP-уведомления): `<URL с Render из шага 6>/yookassa/webhook`,
     события — `payment.succeeded`, `payment.canceled` и `refund.succeeded`
     (последнее — чтобы возврат автоматически снимал Pro/кредит, см. «Возврат
     денег» ниже). Сервер не доверяет содержимому
     вебхука напрямую — при получении любого уведомления перепроверяет
     статус платежа отдельным запросом к самой ЮKassa (см. `src/yookassa.js`),
     так что даже если кто-то подделает POST на этот адрес, ничего не
     произойдёт.

6. **Deploy**. Через пару минут в логах должно появиться
   `meal-planner-server слушает порт ...`. Render сам покажет публичный
   URL вида `https://meal-planner-server-xxxx.onrender.com` — **пришлите
   его мне**, я подключу к нему фронтенд (одна строчка конфигурации).

7. Разово — проверить `https://<ваш-url>.onrender.com/health` в браузере,
   должно быть `{"ok":true}`.

8. На фронтенде (GitHub → Settings → Secrets and variables → Actions →
   Variables) пропишите:
   - `VITE_BACKEND_URL` — тот самый URL из шага 6, без слэша на конце. Без
     этого фронтенд не знает, куда стучаться, и просто работает как раньше,
     без напоминаний/лимитов/истории.
   - `VITE_SUPPORT_URL` — `https://t.me/s_edim_bot` (именно чат с самим
     ботом — см. шаг 9 ниже: сервер умеет принимать и агрегировать такие
     сообщения, поэтому личный аккаунт разработчика указывать не нужно).

9. **(Необязательно, но рекомендуется) Подключите вебхук**, чтобы бот сам
   приветствовал новых пользователей на `/start`, принимал обращения в
   поддержку (кнопка «Написать в поддержку» ведёт именно в чат с ботом, см.
   шаг 8) и отвечал вам на `/report`/`/feedback`. Один разовый запрос
   (замените `<TOKEN>` на токен бота, `<SECRET>` — на значение
   `TELEGRAM_WEBHOOK_SECRET` из шага 5, `<URL>` — на URL с Render из шага 6)
   — выполнить у себя в терминале (Mac: приложение «Терминал»):
   ```bash
   curl "https://api.telegram.org/bot<TOKEN>/setWebhook" \
     -d "url=<URL>/telegram/webhook" \
     -d "secret_token=<SECRET>"
   ```
   `<SECRET>` и значение `TELEGRAM_WEBHOOK_SECRET` в Render должны быть
   **одной и той же строкой** — та, что вы придумали (или сгенерировали) в
   шаге 5, подставляется в обоих местах без изменений.

   Ответ на команду должен быть `{"ok":true,"result":true,...}`. После
   этого:
   - новый пользователь, написавший боту `/start`, получит приветствие с
     инструкцией нажать «Открыть»;
   - любое другое сообщение боту (например, через кнопку «Написать в
     поддержку») сохраняется как обращение, а отправителю приходит короткое
     подтверждение;
   - вы сами можете написать боту `/report` — отчёт по событиям прямо
     сейчас, не дожидаясь ежедневного `DIGEST_HOUR`;
   - `/feedback` — список последних обращений от пользователей;
   - `/backup` — свежий снимок БД документом прямо сейчас, не дожидаясь
     `BACKUP_INTERVAL_HOURS`;
   - `/diag` — отвечает ли ВкусВилл **с сервера** (одна пробная выборка) и
     сколько цен ждёт подогрева. Первое, что запускать, если пользователи
     пишут «каталог не ответил»;
   - скриншот, присланный боту (фото или картинка файлом, можно с подписью),
     сохраняется как обращение и копируется вам сообщением.

## Выдать Pro вручную (для тестирования, не оплачивая)

Оплата подключена (ЮKassa, см. `YOOKASSA_SHOP_ID`/`YOOKASSA_SECRET_KEY` выше и
`POST /api/pay/create` ниже) — но для тестирования или разовых исключений
по-прежнему можно выдать Pro вручную, это отдельный, независимый от оплаты
переключатель (`is_pro`, бессрочный — не путать с `pro_until`, ограниченным
сроком настоящей оплаченной подписки):

```bash
# локально:
DB_PATH=./data.db node scripts/set-pro.js <telegram_user_id> on

# на Render — вкладка Shell у вашего сервиса, там уже стоит правильный DB_PATH:
node scripts/set-pro.js <telegram_user_id> on
```

`off` снимает статус. Свой `telegram_user_id` узнать у @userinfobot.

`off` трогает только `is_pro`, специально не затирая `pro_until` — иначе
снятие ручного тумблера у кого-то однажды могло бы случайно отменить чей-то
реально оплаченный/реферальный период (они независимы, см. `getUserPro` в
`src/db.js`). Если нужно полностью сбросить СВОЙ же аккаунт (например,
увидеть приложение от лица нового пользователя, а до этого тестировали
реферальную программу — `pro_until` уже стоит в будущем) — `set-pro.js off`
тут не поможет, нужен `reset-pro.js`, он снимает и то, и другое разом:

```bash
node scripts/reset-pro.js <telegram_user_id>
```

## HTTP-эндпоинты

Все, кроме `/health`, ждут `POST` с телом `{"initData": "...", ...}` —
`initData` (не `initDataUnsafe`!) Telegram Mini App сам кладёт в
`window.Telegram.WebApp.initData`, сервер проверяет подпись.

| Метод и путь | Что делает |
|---|---|
| `GET /health` | без авторизации, для проверки, что сервис жив |
| `POST /api/vkusvill/call` | `{tool, args}` — прокси к MCP ВкусВилл для фронтенда. Нужен, потому что браузер не может ходить в `mcp.vkusvill.ru` напрямую: CORS-preflight (OPTIONS) отвечает 401 без CORS-заголовков (проверено 04.10.2026). Только известные инструменты, общий кэш на 30 минут, склейка одинаковых запросов, потолок 50 запросов в минуту на наш IP (лимит ВкусВилл — 60) |
| `POST /api/plan` | сохраняет план для напоминаний (перезаписывает предыдущий — один активный план). **Только синхронизация, лимит не трогает** — фронтенд зовёт его на каждое изменение плана, в том числе просто на открытие приложения |
| `POST /api/plan/generate` | авторитетный учёт сборки: Pro — всегда можно; иначе бесплатный слот (`plan_generated`), иначе купленный кредит (`plan_generated_credit`, списывается), иначе 403. Один вызов на реальную сборку |
| `POST /api/account/delete` | `{confirm: true}` — удаляет все данные пользователя (`deleteUserData`); платежи остаются (бухучёт) |
| `POST /api/family/{create,join,leave,status,pantry}` | общий список на семью; работает, пока у ВЛАДЕЛЬЦА активен Pro (`active` в статусе), данные при окончании Pro не удаляются |
| `POST /api/support/prompt` | бот присылает подсказку «напишите обращение сейчас» перед выходом в чат поддержки |
| `POST /events` | событие продуктовой аналитики (воронка, клики, `app_error`) |
| `POST /api/plan-status` | можно ли собрать новый план: `{isPro, proUntil, usedThisWeek, freeLimitPerWeek, extraPlanCredits, canGenerate, nextResetHint}`; заодно сверяет незавершённые платежи этого пользователя у ЮKassa |
| `POST /api/plans` | сохраняет собранный план в историю (не более 12 последних на пользователя) |
| `POST /api/plans/list` | список прошлых планов пользователя, новые сверху |
| `POST /api/meal-times` | обновляет время приёма(ов) пищи для уже сохранённого плана напрямую, без пересборки — иначе новое время из Аккаунта долетало до сервера только вместе с целым планом |
| `POST /api/prices` | `{names: string[]}` → `{prices: [{name, matched, price, productUnit, xmlId}]}` — общий кэш цен ВкусВилл по названию ингредиента (см. `vkusvillPrices.js`), один на всех пользователей; фронтенд (`attachRealCosts`) пробует его первым и откатывается на прямой запрос к ВкусВилл, если он недоступен |
| `POST /api/pay/create` | `{email, product?: "pro"\|"extra_plan"}` — создаёт платёж в ЮKassa (Pro 299 ₽/30 дней или «ещё один план» 59 ₽; Idempotence-Key детерминированный — двойной тап не создаёт второй платёж), возвращает `{confirmationUrl}` — фронтенд открывает её через `Telegram.WebApp.openLink`; 503, если `YOOKASSA_SHOP_ID`/`YOOKASSA_SECRET_KEY` не заданы |
| `POST /yookassa/webhook` | уведомление ЮKassa о смене статуса платежа — **без** проверки `initData` (это не Telegram, а сама ЮKassa) и **без** доверия статусу из тела запроса: сервер перепроверяет реальный статус отдельным запросом к ЮKassa своими учётными данными, только тогда выдаёт оплаченное. Понимает `payment.*` и `refund.*` (возврат берётся из `object.payment_id`), прочие семейства событий игнорирует |
| `POST /api/referral/claim` | `{referrerTelegramId}` → регистрирует "меня пригласил такой-то" (см. `referrals.js`) — награда начислится позже, когда приглашённый реально соберёт первый план (см. `POST /api/plan`) |
| `POST /api/referral/status` | `{rewardedCount, daysEarned}` — сколько людей пригласил пользователь и сколько дней Pro это принесло |
| `POST /telegram/webhook` | входящие сообщения от Telegram: `/start` → приветствие, свободный текст → сохраняется как обращение в поддержку, `/report`/`/feedback`/`/backup` от админа → отчёт/список обращений/снимок БД сейчас же — требует заголовок `X-Telegram-Bot-Api-Secret-Token`, см. `TELEGRAM_WEBHOOK_SECRET` и шаг 9 деплоя |

## Файлы

- `src/initData.js` — проверка, что запрос действительно пришёл из
  Telegram Mini App (без пароля/логина — официальный механизм Telegram).
- `src/db.js` — SQLite (`node:sqlite`, встроен в Node, доп. зависимость не
  нужна): планы, события, Pro-статус, история планов.
- `src/reminderTiming.js` — чистая математика "пора ли напомнить прямо
  сейчас" (часовые пояса, минуты до приёма пищи).
- `src/telegram.js` — отправка сообщений/документов через Bot API.
- `src/scheduler.js` — один "тик": найти, кому пора, отправить, пометить.
- `src/app.js` — HTTP-эндпоинты, см. таблицу выше.
- `src/digest.js` — отчёт по событиям/ошибкам разработчику в личку, по
  расписанию (`runDigest`) и по требованию через `/report` (`sendDigestNow`).
- `src/backup.js` — бэкап БД тем же способом (документом в тот же чат), по
  расписанию (`runBackup`) и по требованию через `/backup` (`sendBackupNow`).
- `src/webhook.js` — что ответить на входящее сообщение Telegram (`/start`,
  `/report`, `/feedback`, `/backup`, свободный текст → обращение) — чистая логика, без
  сети; сама отправка и запись в БД — в `app.js`.
- `src/vkusvillPrices.js` — общий кэш цен ВкусВилл по названию ингредиента
  (см. `POST /api/prices` в таблице выше), с живым запросом к ВкусВилл на
  промах кэша.
- `src/yookassa.js` — тонкий клиент API ЮKassa: создать платёж, проверить
  его реальный статус напрямую (см. `POST /yookassa/webhook`).
- `src/payments.js` — что делать с ПЕРЕПРОВЕРЕННЫМ статусом платежа: выдать
  оплаченное (идемпотентно), снять при полном возврате, пометить `review`
  чужой платёж/несовпадение суммы, алерт админу; сверка зависших `pending`
  (раз в 10 минут и при `/api/plan-status` самого пользователя).
- `src/maintenance.js` — уборка БД раз в 6 часов: события старше 90 дней,
  кэш цен старше 30 дней, надгробия удалённых аккаунтов старше года.
- `src/warmup.js` — фоновый подогрев (раз в минуту): страницы рецептов самых частых
  фильтров (спрос копится в `warm_targets` + 6 базовых страниц) и цены их
  ингредиентов обновляются заранее — рецепты после 4 ч (срок кэша 6 ч), цены после
  8 ч (срок 12 ч). Работает только при нагрузке на лимит ВкусВилла ниже 25 из 50
  запросов в минуту, уступая пользователям. Предсказывать цены не пытается — только
  не даёт данным устареть.
- `src/vkusvillProxy.js` — прокси каталога ВкусВилл для фронтенда (кэш,
  склейка запросов), `src/catalogMonitor.js` — проба «отвечает ли ВкусВилл с
  сервера» раз в 10 минут и алерт админу после двух неудач подряд,
  `src/http.js` — `fetch` с таймаутом для ЮKassa/Telegram и защита тиков от
  наложения.
- `src/rateLimit.js` — лимиты запросов в памяти (по пользователю, по IP
  вебхука) и бюджет живых запросов к ВкусВилл.
- `src/family.js` — общий список на семью.
- `src/proRenewal.js` — напоминание "подписка скоро закончится" (обещано в
  `public/terms.html`), по расписанию, тем же ботом.
- `src/referrals.js` — реферальная программа: и пригласивший, и приглашённый
  получают дни Pro, награда — по факту первого собранного плана приглашённым
  (см. `POST /api/referral/claim`, `POST /api/plan`).
- `src/index.js` — точка входа, читает переменные окружения, запускает
  сервер и все таймеры (напоминания + дайджест/бэкап/напоминание о продлении).
- `scripts/set-pro.js` — ручная выдача Pro, см. выше.
- `scripts/reset-pro.js` — полный сброс Pro (и `is_pro`, и `pro_until`) для
  одного пользователя, см. выше.
- `scripts/grant-credit.js` — начислить пользователю разовые планы вручную
  (`node scripts/grant-credit.js <id> [сколько]`), например когда бесплатный
  план сгорел на сбое.
- `scripts/delete-user.js` — удаление всех данных пользователя по запросу
  (та же `deleteUserData`, что у кнопки «Удалить мои данные» в приложении).

Тесты — рядом с каждым файлом (`*.test.js`), `npm test`.

## Инварианты — их нельзя ломать, даже если «так удобнее»

1. **Между проверкой и записью в обработчике — ни одного `await`.** Гонок нет
   не из-за блокировок, а потому что процесс один, а `DatabaseSync`
   синхронный: проверка бесплатного лимита → запись события → списание
   кредита в `POST /api/plan/generate`, идемпотентность в `applyPaymentStatus`,
   пометка реферала до отправки сообщения. Один добавленный `await` посреди
   такой последовательности вернёт гонки (двойная выдача, двойное списание).
2. **Личность — только из подписанного `initData`**, никогда из тела запроса.
3. **Оплаченное выдаётся только по статусу, перепроверенному у самой ЮKassa**
   (тело вебхука не подписано). То же для возвратов.
4. **`plan_generated` пишет только сервер**, в `/api/plan/generate`. Клиентское
   `/events` с этим именем молча игнорируется.
5. **Один инстанс.** Лимиты запросов и сверка платежей держат состояние в
   памяти процесса; горизонтальное масштабирование их сломает.
6. **Миграции — только добавление колонок** (`ensureColumn`), постоянный диск
   не пересоздаёт таблицы. Версионирования схемы пока нет.

## Ранбуки

**Возврат денег.** Сделать возврат в личном кабинете ЮKassa (платёж → «Вернуть
платёж»). Вебхук `refund.succeeded` (должен быть включён, см. выше) подтверждается
запросом к ЮKassa, платёж получает статус `refunded`, полный возврат автоматически
снимает 30 дней Pro (но не глубже «сейчас») или один кредит «ещё одного плана»;
вам в личку придёт алерт. Частичный возврат ничего не меняет сам — только алерт.

**Пользователи пишут «каталог ВкусВилл не ответил» / планы без цен.** Написать боту
`/diag`. «Отвечает» — проблема у конкретного пользователя (проверьте `/api/vkusvill/call`
в логах). «НЕ отвечает, HTTP 401/403» — ВкусВилл (QRATOR) блокирует адрес нашего
сервера, нужен хостинг в РФ. Админу также приходит алерт сам (две неудачи подряд).
Пока каталог недоступен, приложение собирает план из базового набора и **не
списывает бесплатный план**; компенсировать уже сгоревшие: `node scripts/grant-credit.js <id>`.

**Первые пользователи после деплоя ждут сборку дольше.** Кэш холодный (он в памяти и
очищается при перезапуске; цены в БД переживают). `/api/prices` отвечает не позже чем
через 18 с тем, что успел, остальное досчитывается в фоне; приложение само повторяет
получение цен до двух минут и не списывает бесплатный план, пока цен нет. Подогрев
(`warmup.js`) заполняет базовые страницы и цены в первые минуты после запуска.

**Платёж завис в `pending`.** Дайджест покажет «платежей в ожидании дольше часа».
Сервер сам сверяет такие платежи раз в 10 минут (до 48 часов с создания) и при
каждом открытии приложения пользователем. Если всё равно висит — проверьте в
кабинете ЮKassa URL вебхука (`<URL>/yookassa/webhook`) и подписку на события.
Статус `review` — платёж с чужим получателем или другой суммой: оплаченное **не**
выдавалось, разбирайте вручную (алерт пришёл в личку).

**Удалить данные пользователя** (запрос через поддержку): Render → Shell →
`node scripts/delete-user.js <telegram_user_id>`. Платежи остаются (бухучёт).
Копии в бэкапах (Telegram-чат) удаляются отдельно вручную.

**Восстановить базу из бэкапа.** Скачать нужный `sedim-ГГГГ-ММ-ДД.db` из чата с
ботом, остановить сервис (Render → Suspend), заменить файл по пути `DB_PATH`
(`/data/data.db`) скачанным (Render Shell/SSH), запустить сервис. Бэкап —
консистентный снимок `VACUUM INTO`. Если база выросла больше ~45 МБ, бэкап через
Telegram перестаёт отправляться (лимит Bot API 50 МБ) — вам придёт предупреждение,
пора выбирать другое хранилище для копий.

**Сменить токен бота.** @BotFather → `/revoke` → новый токен → `TELEGRAM_BOT_TOKEN`
в переменных Render → заново выполнить `setWebhook` (шаг 9) → проверить `/health` и
отправку напоминания. Подпись `initData` проверяется по токену, так что до обновления
переменной все запросы приложения получат 401.

**Сменить ключ ЮKassa.** Выпустить новый секретный ключ в кабинете, обновить
`YOOKASSA_SECRET_KEY` в Render, перезапустить, создать тестовый платёж.
